# Task board

The task board tracks every Midna Claude session and its task. Hooks report turns and commits; you report the rest. "The owner" is the person who runs the board.

If a bare `tb` isn't on the PATH, use `${CLAUDE_PLUGIN_ROOT}/bin/tb`. The `.md` files named here sit next to this one.

## When you're on a task

You're on a task when your prompt or context starts with `[task-board:T<n>]`, or after `tb take T<n>`. Then:

- **At milestones**, save a checkpoint a new terminal can resume from:
  `tb checkpoint --done "what's finished" --next "what's next" --decision "a choice to keep"`
  Flags repeat; `--file path` for key files.
- **Notes** worth keeping: `tb note "..."`. For the whole goal: `tb note --goal --kind finding|decision|reference "..."`.
- **Lessons** that should outlast the goal: `tb lesson add "<what to do differently>" --kind planning|code|process|tooling` (`--global` for every project). A goal note is for this goal's tasks; a lesson is for later work: a trap in the code, a step that keeps failing, a plan that had to be redone. One or two sentences, saying what to do. It's suggested until the owner keeps it (`tb lesson keep L<n>`, only on their word); kept ones reach later handoffs in the project (the few that fit the task best, by its words and the code it's likely to touch), and planning ones reach planners. Later work that shows the same thing again: `tb lesson confirm L<n> --evidence T<n>`. `tb lessons` lists them; `tb lesson search "<words>"` finds the ones that fit. Lessons also look after themselves: after each goal's retrospective, a suggested lesson confirmed by two goals is kept, one that five goals in its scope went by without confirming is retired, and a project lesson confirmed in two projects is marked "make global?" for the owner. `tb planning --suggest` shows the edit that writes the project's kept planning lessons into its planning file; `tb planning --accept` writes it, only on the owner's word. `tb quality` shows how well goals were planned, by month.
- **The owner asks for something else**: the board asks on each of their prompts whether it's part of this task. Small follow-ups to the same change are; a separate fix or feature (its own commit or PR) isn't. Split separate work off before you start on it, without asking:
  - `tb task new "<title>" --detail "<the ask>" --here --next` queues it in this terminal after the current task; carry on with the current one.
  - `--here --now` switches to it now; the current task waits here to resume. Commit or stash its changes first when they share the checkout.
  - `tb switch T<n>` moves to a task in this terminal's line; `tb line` lists the line; `tb line drop T<n>` sends one back to the board.
- **Tests**: run only the tests that cover what you changed (the crate, package, module or test file you touched, e.g. `cargo test -p <crate>`, `flutter test test/<area>`), never the whole suite. CI runs the rest; when a CI check fails, run the failing tests and the ones covering your fix.
- **Long builds and tests**: anything that may run past a couple of minutes (`cargo build`, `cargo test`, `flutter test`) goes in the background (`run_in_background: true`); end your turn or keep working, and Claude Code tells you when it exits. Never poll it with a `sleep` loop, and never wrap it in a foreground command that can hit the 10-minute timeout: the output is lost and you run it again. Run `cargo check` before `cargo test`, so a compile error costs seconds, not a test build.
- **Something outside the task**: don't fix it. Report it and carry on:
  `tb found "<short summary, 80 chars max>" --kind bug|gap|follow|clean --detail "what you saw" --output "error text"`
- **The goal's own done-when isn't met** (you see its outcome miss, e.g. on one platform): `tb found "<what misses>" --misses-goal`. It goes to the owner as an alert, not quietly to the backlog, and the goal stays open until the miss is made into a task that's done, sent to Jira or closed.
- **Work in another repository**: a task's work stays in its own project's repository. The board refuses edits, commits, pushes, new worktrees and PRs in any other repository, and tells the owner. Work there needs its own task in that repository's project: `tb found` it, or `tb task new "<title>" --project <its project>` (`midna project add <dir>` when the board has no project for it). When the task itself was filed under the wrong project, move it instead and carry on: `tb task set T<n> --project <its project>`.
- **Worktrees**: every worktree a task works in is a slot from the board's pool, `<repo>/.claude/worktrees/slot-<n>`, reused from task to task so builds stay warm and the disk doesn't fill. Don't make your own: from a task's terminal the board refuses `git worktree add`, `EnterWorktree` and subagents with `isolation: worktree` outside the pool. A goal that runs its tasks in worktrees starts each in a slot, detached at the base; make your branch there with `git switch -c`. The task holds its slot until it submits, fails or parks with `tb wait-for`, and gives it back then; that's refused while the slot has uncommitted changes or unpushed commits (commit and push them, or discard them). `tb slots` lists each slot, who holds it, who waits, when it was last used and its size. `tb slot claim` takes one for review fixes, a rebase or a failing check (its own again when free, on the pushed branch) and prints its path; `tb slot release` gives it back early; `tb slot discard [path]` saves a slot's uncommitted changes to a backup ref and clears them. When the task starts again in its slot, the board clears files it never edited that match its base (saved to a backup ref first) and rebases a clean, unpushed branch onto the base; its log says what it did. While the pool is full the task waits for a slot (`tb locks` lists `wt:slot-<n>`). A task with no worktree works in the shared checkout: commit only your own files, by name (the board refuses a commit of another task's edits there). In a file another task edits too, only your own hunks may go in: `tb stage [files]` stages just those from your recorded edits (a file only you edited goes whole; a hunk you both changed is refused naming the other task), then `git commit` without `-a` or a `git add` of that file. Any task (one made with `--here`, or outside a goal) can move to a slot when it wants its own: `tb slot claim --bring <files>` takes a slot, puts the task on the slot lane and moves its uncommitted edits in those files there from the shared checkout (`--bring` on its own takes the files the task edited; in a file another task is editing too, only your own hunks go and theirs stay, a hunk you both changed is refused naming the other task, and hunks no task's edits made (shell edits) are listed with ids: pick yours with `--bring-hunk <file>:<id>`, or leave them with `--bring-hunk none`; a refusal or clash changes nothing). Then `cd` to the path it prints and carry on there; if it says the slot is detached at your branch's tip, make a new branch with `git switch -c`. `tb task new "<title>" --here --lane slot --bring <files>` does the same for a new task. Subagents work in the task's checkout: give each its own files.
- **Needs another task's unfinished work** (any goal): `tb wait-for T<n> --why "…"` (add `--merged` when you need its PR merged first), then end your turn. Never ask the owner; see `questions.md`.
- **Blocked on the owner**: read `questions.md` first; most calls are yours. Still the owner's? `tb question "<the question>"`, then stop. Answered another way since? `tb withdraw "<how>"`.
- **Needs something only the owner can do** (make an account, sign an agreement, buy something, get a key from a site you can't reach): make a human task, H<n>: `tb task new "<what to do>" --human --detail "<numbered steps, each link written out, and what to send back>"`, then `tb wait-for H<n> --why "…"` and end your turn. No agent works on it: the owner follows the steps and presses Done in the app with a note, and you carry on with that note in your prompt. The steps hold everything they need and nothing for you; one H task per thing they do.
- **Something made for the task**: `tb attach <url-or-path> --kind design|proposal|doc|evidence|results|other --title "..." --summary "..."` (`--goal G<n>` for the goal). A claude.ai artifact link takes the artifact's own title as `--title`; the board can't open it to read one. Don't attach writing as a loose file (.md, .txt, .rst, .html): publish it as a brief artifact and attach that link; the board refuses those files.
- **Written results**: attach a link with `--kind results`. Lead with the answer.
- **A design is attached**: open it before you touch UI and build to it; note anything that can't match.
- **Not on the default branch**: unless the owner turned it off, the board refuses a `git commit` on a repository's default branch (main) and a `git push` that lands on it. Commit on a branch of your own (`git switch -c <branch>` carries uncommitted edits along) and land it through a PR.
- **No code comments** (Python docstrings count too) when your handoff says so: the owner's comment guard is on. Make the code say it (names, small functions) and put the why in the commit or PR; pragmas the tools read (`# noqa`, `// eslint-disable-next-line`, …) are fine. The board refuses an edit that adds a comment, and the PR, `tb pr wait` and `tb submit` while the branch adds any.
- **The owner's steps** (in your handoff, or `tb steps`): work the owner wants on every task in this project, before the PR or before `tb submit`, in order. Each says how to get past it:
  - agent work: do it as its prompt says, then `tb step done "<name>" --note "what came of it"` (it runs the step's check first; fix what fails);
  - a script: `tb step run "<name>"`, fix what it reports and run it again (it can take a while: give it time);
  - the owner's: `tb step ask "<name>"`, then end your turn; the board brings you back once it's done.
  A step that can't pass: `tb step fail "<name>" --why "…"`, then end your turn. The board refuses the PR and `tb submit` while one is left.
  A review step may report findings: `tb steps` lists them with their ids. Fix each, then `tb step triage "<name>" F2 --state fixed --commit <sha>` (or `answered`/`dismissed` with `--note "why"`), and `tb step again "<name>"` for another round (add `--branch <b>` or `--worktree <dir>`, and/or `--commit <ref>`, to aim it at something other than this checkout's head; `tb step aim` with the same flags saves the aim so later rounds and the gates follow it, and `tb steps` shows it; a pinned `--commit` is dropped once its branch gets a new commit, and a detached checkout takes `--worktree <dir> --branch <b>` together, judged on the branch's tip, which must contain the checkout's head). After a rebase's push (once the task has a PR), `tb step publish "<name>"` republishes a review step's result for the new head (`tb pr status` lists it in the rebase commands). A step that runs per push needs a round on each new commit; rounds may need a gap between them (the refusal says when).
- **Review findings** (a review step, a reviewer, a check): fix only what this task's change caused. A finding on code the change didn't touch goes to the backlog (`tb backlog add … --kind follow`) and is dismissed in the review with a line saying so. Never reverse an earlier decision (a goal note, a checkpoint `--decision`, an owner's answer) to satisfy a finding.
- **Jira** (when the board has it on: your handoff has a `Jira:` line or names a ticket): read `jira.md`. Never ask the owner which ticket.
- **At the end**: `tb submit "<summary>" --human <time>`, or `tb fail "<why>"` if it can't be done. The summary is for the owner, not another agent: one or two short plain sentences on what's different now or what was found, with little to no jargon (no file, function, query or header names, no task and backlog refs). The details belong in the PR, a note or an attached doc. When this terminal has a line, `tb submit`, `tb fail` and a `tb wait-for` that parks the task move it on to the next task and print its handoff: carry straight on with it. Outside work hours or with the 5-hour usage used up nothing moves on; the next task is sent here once they open or the usage resets. `--human` is your honest estimate of how long this task would have taken a developer by hand (`3h`, `90m`, `1d`); the Days page compares it with your time. A PR, now or later? Read `pr.md` first: the board opens it (`tb submit "<summary>" --pr-body <file>`); `--pr <link>` is only for a PR that was open before the task.

`tb status` shows this terminal's task and its line (with the board down it says so and fails; it saves nothing). Every command takes `--task T<n>`. If the board is down, `tb` saves reports and sends them later.

The goal's setup (`Set up (every task in this goal does this)` in your handoff) comes before anything else, and it overrides the handoff's branch name when it names one. Set it only when the owner asks: `tb goal setup G<n> "<what every task does first>"` ({task}, {n}, {wave}, {goal} and {jira} (the ticket key, else the task ref) are filled in per task, {device} and {target} ({device2}, {target2}…) with the devices lent to it; `none` clears it).

## When you're the Jira desk

Your first prompt says "You are the task board's Jira desk", and each job starts `[task-board:J<n>]`. Follow `jira.md` ("The Jira desk"): search first, make a ticket only when none covers the work, report with `tb jira J<n> ok key=… status=…` or `tb jira J<n> fail "<why>"`, and keep the terminal open.

## When there's no task

The owner's questions, screenshots and asks in this terminal are the task. Once you change code for them, put it on the board as a task on this terminal, without asking. If an open backlog item in the project already covers the work, take it: `tb task new --issue B<n> --here`. Otherwise make a standalone task:
`tb task new "<short imperative title>" --detail "<what the owner asked for and what you're changing>" --here`.
When the work is a design (concepts, a canvas, mockups, a design artifact), the build work comes after it, so start a goal for the feature first: `tb goal new "<feature>" --tldr "…" --outcome "<done when>"`, then the design task in it on this terminal: `tb task new "<title>" --detail "…" --kind design --goal G<n> --here`. The implementation tasks that follow go in that goal (`tb task new --goal G<n>`, or `tb propose G<n>`), not on their own; they wait for its open design tasks unless given `--waits-for none`. A design task ends without a PR: attach the design (`tb attach <canvas or mockup link> --kind design --title "…"`), then `tb submit "<summary>"`. `tb task set T<n> --kind design|none` changes an existing task.
You're on it at once; from then on follow "When you're on a task". Take it to the end yourself: once the change works and its tests pass, ship it in the same turn (commit, rebase, push, `tb submit "<summary>" --pr-body <file>`) and don't stop at "it's on the branch" for the owner to say "push it". Wait first only when they asked to look before it ships. A turn that ends with the task's work committed and no PR is told by the board to ship it. `--here` only takes this terminal's project's work: for another repository, make the task with `--project <its project>` and no `--here`. When Midna has no project for this terminal's folder, `--here` is refused; add one with `midna project add <dir>` (the refusal names it), then run it again. If a turn changes code with no task, the board stops it, lists the project's open backlog items and asks for this.

Finding work: `tb search "<words>"` finds tasks, backlog items, goals and notes; `tb tasks` (`--goal G<n>`, `--status`) and `tb backlog list` list them; `tb task show T<n>` and `tb backlog show B<n>` read one. Search before making a task or backlog item that may already be there.

Otherwise don't run `tb` unless the owner asks you to take, report, find or add something. PR work on a done task: `pr.md`.

## Putting things on the board

The owner can't make or change anything in the Taskboard app: new tasks, goals and issues, notes, edits, moves and attachments all go through you when they ask. The app only starts and stops work.

Planning a goal? Read `planning.md` first.

1. Reuse an open goal that fits (`tb goals`; `--project <name>` narrows it).
2. Pick the smallest thing that fits:
   - An effort with an outcome: `tb goal new "<name>" --tldr "…" --outcome "<done when>" --task "title::what to do"` (repeat `--task`). Tasks for an existing goal: `tb propose G<n> --task "title::detail"`. Tasks that run side by side in a wave can name the files each will edit, so its wave mates leave them alone: `--task "title::detail::<wave>::::src/a.rs, src/b.rs"` (or `tb task new --goal G<n> --wave 2 --file src/a.rs`).
   - One piece of work: `tb task new "<title>" --detail "..." [--goal G<n>]`. Check the project's open backlog first (`tb goal show G<n>` lists a goal's): when an item covers it, use `tb task new --issue B<n>` (`--here` to take it on this terminal) so the item and the task don't both stay open.
   - Only a human starts a task or runs a goal. When the owner asks you to start, queue or run one ("start T4", "make a task and queue it", "run G2"), run `tb start T<n>` / `tb start G<n>` (`--queue` to wait for a free terminal) and trust the board: it reads each prompt as it is typed and tells you whether it is a start word. Never on your own. "Start the goal" means `tb start G<n>`, which runs its tasks in their waves: never start a goal's tasks one by one. Outside work hours a goal's tasks wait for the hours to open; when the owner says to run it now anyway ("run G2 now"), `tb start G<n> --now` runs that goal alone until they open. Only goals take `--now`. When you ask, name it ("Want me to run G2?").
   - More than one piece of work talked over, and the owner says to start ("go ahead and start", "start", "go"): put them all in one goal and run it, so they don't have to start each. When they're already in one open goal, `tb start G<n>`; otherwise `tb goal new "<name>" --tldr "…" --outcome "…" --task "title::what to do"` (a `--task` each), then `tb start G<n>` in the same turn. Never make them loose tasks and start them one by one. One piece of work stays a task.
   - The owner's `/start [T<n>|G<n>|the goal]` command, and a prompt that ends in a lone "go" ("make a task for the footer. go", "T8 go"), always count as their word: `/start` with nothing named means this terminal's task or what you make this turn; "go" starts what the prompt makes, or else what it names. Run `tb start` for it.
   - If the board refuses, don't retry or rephrase: the owner gets a notification to start it. A task waiting on unfinished work (`tb wait-for`, a stack parent) can't start until that's done. Never read the board's `app-token` file or its `app.sock`; they're only for the app.
   - Another goal's task does it: `tb task set T<n> --also G<n>`.
   - Waves, waits, locks, running alone, worktrees, devices and bits (feature flags): `planning.md`.
   - Something to remember, not do now: `tb backlog add "<title>" --kind bug|gap|follow|clean --detail "..." [--goal G<n>]`.
   - Retitle or rewrite an issue (the owner asks you to): `tb backlog set B<n> --title "..." [--detail "..."]`.
   - Move issues to another goal, or out of their goal: `tb backlog move B<n> [B<n> …] G<n>|none` (several move together or not at all).
   - Filed under the wrong project (found in one repo, but the fix belongs in another): `tb task set T<n> --project <name>` or `tb backlog set B<n> --project <name>`. It keeps its goal. A task moves in any state: one you're on stays on this terminal and you carry on in the new project's repo (the board refused work there until the move), one with a PR keeps it, and a done one waits in the new project's Unreleased. Only a task stacked on another (`--stack-on`) has to be unstacked first.
   - Add a note to an issue's log, keeping its detail: `tb backlog note B<n> "<text>"`.
   - What needs the owner (the app's Needs you list), when they ask to go through it with you: `tb needs` lists it (`--project <name>`, `--json`), `tb needs show <item>` shows one in full with its options and the commands for it. Act only on their word, one item at a time: `tb needs answer <item> "<their answer>"` (or `--pick <n>`, one per question of a picker), `restart`, `finish`, `continue` (a wave stop), `dismiss`, `snooze <item> [--mins N | --until tomorrow|back]`. A human task's Done and a weekly review stay the owner's, in the app.
   - Close the terminals of finished tasks when the owner says so: `tb close --done` (`--project <name>` or `--goal G<n>` to narrow it; a terminal still busy is left open).
   - On the owner's word, act on an issue: `tb backlog task B<n>` (a planned task in its goal; `--board` queues it on the board), `tb backlog ticket B<n>` (a Jira ticket), `tb backlog drop B<n> --reason "..."` (won't do), `tb backlog reopen B<n>`. Each takes several issues at once (`tb backlog task B4 B5`): all change or none do. To start an item on the owner's word, `tb start B<n>` makes it its task and starts it.
   - The backlog tidy closes repeats and false findings on a timer (a day unless changed). On the owner's word: `tb backlog tidy` (show), `--off`/`--on`, `--every hourly|daily|6h`, `--now`, `--reset`. An issue it closed says why in its log; `tb backlog reopen` undoes it.
   - Run, hold back or bring back a goal when the owner says so: `tb start G<n>` or `tb goal set G<n> --run` (queues its planned tasks; refused without their word to start or run it in this terminal, and outside a Midna terminal, where only Run on the board runs a goal; a refused `--run` saves none of that command's other changes), `--deprioritize`, `--prioritize`, `--paused on|off`.
   - Something the owner must see that isn't a question on your task (a watcher or script you were asked to set up finds main red): `tb alert raise "<what>" --key <name> [--urgent] [--task T<n>]`, and `tb alert clear <name>` once it's fixed. `--urgent` only for what can't wait: it repeats outside the work hours and can't be dismissed.
   - A red default branch the board watches is a break, `M<n>`: `tb master` lists them (`--open` only the red ones, `--limit N` the newest N, 20 by default) and `tb master M<n>` shows the failing checks and suspect commits. The board decides whose it is; `tb master M<n> ours|not-ours|unsure --why "<…>" --title "<the cause in a few words>"` changes that only on the owner's word (`--why` says what broke it and how you checked, 20 to 300 characters; `--title` is 80 characters at most; `not-ours` needs `--title` and `--proof <link>`: the build or issue that shows it; repeat for more). Write the title and why for a person, not a log: plain words and names, no test names, paths, line numbers or build ids. A fix task it made for one is an ordinary task: fix the branch, and the board closes the break when it's green. Its own agent may record `not-ours` (with `--title`, `--why` and `--proof`) or `unsure` (with `--why`) on that break without asking, the same as `tb pr not-ours` on a PR, then finish with no PR; the verdict is credited to its terminal, and once the owner has decided a break their word stands.
   - Whether a project's work ends in PRs, and its PR rules: `tb project show [<name>]`; on the owner's word, `tb project set <name> --pr-flow auto|on|off`, `--approvals N` (approvals a PR needs; 0 = the host decides), `--expected-check "<check>"` (repeat; `none` for none), `--expected-wait <mins>` `--ask-stage on|off` (after the owner's review, the PR waits until you ask its reviewers with `tb pr reviewers`) `--swap on|off` (a reviewer who hasn't reviewed in time is replaced), `--review on|off` (off: its PRs go to merge without reviewers) and `--agents-merge on|off` (you merge its approved, green PRs with `tb pr merge`), `--waits-on <other>[,…]|none` (its tasks may wait for those projects' tasks), `--releases on|off` (it cuts releases; off unless turned on), `--release-tags '<pattern>'|none` (a new matching tag on the default branch cuts a release named after it, holding the work the tag contains), `--release-script '<command>'|none` (what `tb release cut` runs before recording a release); `default` puts a rule back to config.toml's. For every project that doesn't say: `tb project agents-merge [on|off|default]`.
   - Releases (`R<n>`), for a project with releases on: `tb releases` lists them with their task counts and how many done tasks wait in Unreleased; `tb release show R<n>|unreleased` lists the tasks by goal (`--markdown` for a changelog to paste). On the owner's word: `tb release cut <name> [--notes "…"]` puts every task in Unreleased (done, with its PR merged or no PR) in a new release. When the project has a release script (`tb project show`), `tb release cut` is how you make a release: it runs the script in this checkout with the name as its argument and records the release only if the script succeeds; never run the script by hand. When the cut prints `Release run: <link>` (the CI run the release's tag started, on GitHub projects), give the owner that link in your reply so they can watch it finish; `tb release show R<n>` lists it later. `--no-script` records a release that's already out without running it; `tb release cut <name> --after T<n> --after G<n>` (repeat) keeps the cut pending until those tasks are done with their PRs merged and those goals are finished, then the board runs it on its own (script included) and tells the owner if it drops it (one pending cut per project; `tb releases` shows it; `tb release cancel` drops it); `tb release set R<n> --name … --notes …`; `tb release move T<n> R<n>|unreleased`. `tb releases`, `show` and `cut` take `--project <name>` for another project's.
   - A design, proposal, doc or link: `tb attach` as above, with `--task T<n>` or `--goal G<n>`.
   - Remove an attachment by its link, path or title: `tb unattach "<link-or-title>"` with `--task T<n>` or `--goal G<n>`. To change one, unattach it and attach it again.
   - A tester's Jira comment the owner gave you their word on (when QA comments are on): `tb qa task Q<n> --note "<what they said>"` or `tb qa ignore Q<n>`; `tb qa waiting` lists the ones waiting (`--goal G<n>` for one goal's tickets).
3. A goal whose work is through but holds failed tasks another task replaced stays open. On the owner's word only, `tb goal done G<n> --why "<what replaced them>"` finishes it: the failed tasks stay failed and keep counting as failed, and a task that fails later holds it open again. It's refused while a task is still to do, a PR is open or a miss on the done-when is open. Never submit a failed task as done or delete it to close its goal.
4. Delete a goal only when the owner asks: `tb goal delete G<n>` asks whether to keep its tasks (a task that also finishes another goal moves there either way); ask the owner, then run it with `--keep-tasks` or `--delete-tasks`.
5. The project defaults to this terminal's; `--project <name>` picks another.
6. Nothing you add runs until the owner queues or starts it; don't take it unless asked.
7. Give the owner the link `tb` printed.

Titles are short summaries a person reads at a glance (80 characters at most, no test names, paths, commit hashes or error text); all of that goes in `--detail`.

## Context limits

The board compacts its agents' conversations at a token window, compacts a cold conversation (idle over an hour) before resuming it, and resumes a task or PR conversation only while it's small and recent (otherwise it starts fresh from the handoff). It also keeps generated files out of agents' diffs (a `-diff` block in `.git/info/attributes`). `tb limits` shows the limits; change them only when the owner asks: `--compact-window 150k` (0, or at least 50k), `--cold-idle-mins 60`, `--warm-tokens 60000`, `--warm-idle-mins 60` (0 turns one off), `--generated "*.g.dart,Cargo.lock"` (`--project <name>` for one project's own; `none` clears), `--review-gap 10` (minutes between a branch's review rounds, 0 to 240, 0 for none; `--step "<name>"` when more than one step has a gap), `--reset`.

## Work hours

The board starts agents only inside the owner's work hours. `tb hours` shows them; change them only when the owner asks (`tb hours --start 09:00 --end 17:00 --days mon-fri`, `--on`/`--off`, `--until 6am` to keep going until then, past midnight if it has passed today (`--today-until` works the same), `--for 8h` to keep going for a while, `--until off` back to the usual hours, `--alert-every 10` for how often unanswered alerts repeat, 0 for never).

Midna keeps the Mac awake during the work hours so agents keep running while the owner is away (idle sleep only: the display still sleeps and closing the lid still sleeps). The work hours are its schedule: `tb hours` changes both, and `--until`/`--for` run both on (or end both early), then the usual hours return. `tb keep-awake` shows whether it's held and why. Change it only when the owner asks: `--on`/`--off`, `--mode with-work|always`, `--min-battery 20` (on battery it lets the Mac sleep below this), `--linger 5`, `--day fri=9am-3pm` / `--day sat=off` / `--day fri=default` for one day's own keep-awake hours, `--today off` / `--today clear`.

Midna's status bar shows the selected terminal's goal, task and line (the app's `plugin/task-board/bin/midna-status`, which runs `tb peek --midna`; `tb peek` alone prints the terminal's whoami as JSON and only reads). `tb status-bar` shows what it includes; change it only when the owner asks: `--goal on|off`, `--title on|off` (off shows refs only), `--reset`.

`tb terminals` shows how many task terminals run across the board and the cap (default 8); tasks over it wait with "Waits for a free slot" and start as slots free. Change it only when the owner asks: `tb terminals --max N` (1–50) or `--max default`.
